# 评测设计

评测目标是分别回答三个问题：模型是否理解用户目标，结构化计划是否正确，以及计划通过真实运行时后是否完成预期任务。

## 数据

冻结 dev 集包含 123 个项目自建 case，覆盖商品、订单、物流、政策、售后、多意图、必要澄清和人工升级。真实模型与关键词基线使用同一套仓库演示数据，避免因业务夹具不同造成不可比较的分数。

数据不是外部客户流量，因此结果只描述这套冻结数据上的能力。

## 指标

| 指标 | 含义 |
|---|---|
| 意图 Core Macro-F1 | 对 11 个有 gold support 的业务意图分别计算 F1 后取平均 |
| exact handoff | 计划能力集合与 gold 必需能力集合完全一致，既不能漏报也不能超报 |
| 真实任务完成率 | 合法计划进入同一 A2A 运行时，必需读取成功并到达期望终态，且没有未请求写 |
| 不必要澄清率 | 信息已经足够的请求中，系统仍要求用户补充信息的比例，越低越好 |

`MULTI_INTENT` 是辅助标签，dev 集中的 gold support 为 0。主指标因此采用 11 类 Core Macro-F1；12 类兼容值单独保留，避免改变类别口径后仍沿用同一个名称。

任务完成率的分母为 117：123 个 case 中有 6 个“数据冲突后向用户澄清”的样例缺少对应冲突世界夹具，因此从该指标排除并明确记录。写请求到达等待确认即满足本轮期望终态，不能解释为业务动作已经提交；指标也不评价最终回答文案质量。

## 对照

- **关键词基线**：使用确定性关键词路由和相同的执行环境，说明结构化模型相对简单规则的变化。
- **oracle**：根据 gold 构造输入，用来检查评测链和指标是否存在可达上界，不代表线上系统能力。
- **负控**：空输出、永远澄清、错实体、漏目标和越权能力应产生明显退化，用于发现指标失灵。

## 证据

[`evidence/summary.json`](evidence/summary.json) 保存机器可读汇总与文件哈希；真实模型、关键词基线和 oracle 的逐例结果分别保存在同目录 JSON 文件中。真实模型证据包含模型别名、输出预算、prompt 版本、数据上下文和延迟信息，不包含 API Key。
